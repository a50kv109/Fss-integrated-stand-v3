# Архитектура двух стендов FSS (TWO_STAND_ARCH)

**Статус:** Проектная спецификация (Предложение)  
**Дата:** 2026-10-13

## Введение
Данная спецификация описывает архитектурный переход от монолитной классификационной системы к двухуровневой модели, состоящей из Справочного стенда (Стенд №1) и Экспериментального стенда (Стенд №2).

---

## 1. Ответственность стендов

### Стенд № 1: Справочно-математический (Существующая функциональность)
*   **Задача:** Хранение полного реестра, валидация математической модели, проверка групп.
*   **Режим работы:** Неограниченный по объему данных.
*   **Функция:** Подготовка данных для Стенда №2.

### Стенд № 2: Экспериментальный (Проектное предложение)
*   **Задача:** Проведение экспериментов с ограниченным набором групп.
*   **Режим работы:** Управляемое рабочее пространство (3–5 активных групп).
*   **Функция:** Импорт данных из Стенда №1, локальный классификационный анализ.

---

## 2. Формат обмена `.fsspack` (Проектное предложение)

Пакет представляет собой JSON-архив с версионированием.

```json
{
  "manifest": {
    "version": "1.0.0",
    "kernel_compatibility": ">=1.0.0",
    "checksum": "sha256:..."
  },
  "passport": { ... },
  "verification": { ... }
}
```

---

## 3. Компоненты пакета
1.  **Паспорт группы (`passport`):** Идентификатор, HM-символы, матрицы операций, трансляции, происхождение (Gemmi/ITA).
2.  **Паспорт проверки (`verification`):** Список проведённых тестов (замкнутость, тождество, инверсия), их результаты и ограничения.

---

## 4. Контроль целостности
Целостность обеспечивается полем `manifest.checksum`. Контрольная сумма вычисляется по конкатенации JSON-объектов `passport` и `verification` (в каноническом представлении).

---

## 5. Процедура импорта и проверки (Проектное предложение)
Стенд №2 выступает в роли "привратника" (Gatekeeper):
1.  **Загрузка:** Чтение `.fsspack`.
2.  **Верификация:** Проверка контрольной суммы по манифесту.
3.  **Аудит:** Проверка записей `verification.json` на соответствие требованиям эксперимента.
4.  **Активация:** Импорт в локальное хранилище данных Стенда №2.

---

## 6. Жизненный цикл групп в Стенде №2
*   **Локальное хранилище:** База данных импортированных групп.
*   **Рабочий набор:** Подмножество групп, загруженных в память классификатора для текущего эксперимента.
*   **Управление:** Импорт, активация, временная выгрузка, удаление из локального хранилища.

---

## 7. Совместимость версий
Версионирование осуществляется по паре `(версия формата пакета, минимальная версия ядра)`. Несовместимые версии отклоняются на этапе проверки манифеста.

---

## 8. Поведение при ошибках
*   **Несовместимость ядра:** Отказ в импорте с сообщением о требуемой версии.
*   **Неполные данные:** Отказ в импорте, если нарушена структура паспорта.
*   **Ошибка контрольной суммы:** Подозрение на коррупцию данных, отказ в импорте.

---

## 9. Доверие и проверка
Важно различать **целостность файла** (пакет не поврежден при передаче) и **математическую доказанность свойств** (паспорт проверки). Стенд №2 может доверять результатам проверок Стенда №1 или (опционально) запускать повторную валидацию локально.

---

## 10. Пример: Пространственная группа P4₁
*   **Стенд №1:** Содержит полную запись P4₁ в реестре (`registry.ts`), выполняет проверки (уже реализовано).
*   **Стенд №2:** Не содержит P4₁ по умолчанию. P4₁ импортируется через `P41.fsspack` только по требованию исследователя.

---

## Заключение

### Критерии приёмки спецификации
1.  Корректное описание механизма импорта/экспорта.
2.  Чёткое разделение ответственности стендов.
3.  Определение структуры `.fsspack` как расширяемого формата.

### Открытые решения
1.  Механизм автоматической синхронизации версий ядра между стендами.
2.  Формат представления результатов экспериментов во втором стенде (нужен ли `results.fsspack`?).
3.  Метод обработки зависимостей, если группа требует сложного вычислительного модуля.
